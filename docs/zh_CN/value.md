# 本项目在哪些方面起到了节省的作用

本项目能在三个方面带来显著节省，其中第三点尤其值得关注。

| 方面 | 说明 |
|---|---|
| **上下文（指大语言模型单次会话的上下文）** | 大语言模型单次会话可读入的内容有限。一份数千行的 job 日志变成一次 `grep` 加几行上下文；一个包含多个 job 的矩阵变成一份名册，而不是多份原始日志 |
| **实际耗时** | 等待变成一次有界调用；取消与去重避免无谓消耗的 runner 时间 |
| **错误结论** | 回答“第 1 次执行失败、第 2 次执行通过”，而不是“这个后端不稳定” |

前两个方面缺失时，使用者只会变慢；第三个方面缺失时，使用者会写出一份看起来有据、实际错误的报告，而别人会依据这份报告做决策。

## 一次工作会话的实测

以下数据来自一位使用者的记录，是他的估算，不是基准测试。

| 问题 | 不使用本服务 | 使用本服务 |
|---|---|---|
| Oracle job 为什么失败 | 一个 job 的 4369 行日志 | `grep: "DPY-6005"`，19 个行号加上下文 |
| 12 个 job 中哪个失败了 | 12 份日志，约 48000 行 | `get_run` 返回名册 |
| 这十个仓库是否全部通过 | 读取十次 | `recent_runs` 一次调用 |

使用者指出最关键的不是比例：完整的矩阵日志根本无法放进大语言模型的会话上下文窗口，所以问题不是“更便宜”，而是“原本无法完成”。
同一天，`cancel_run` 与 `if_absent` 粗算节省 50–60 分钟 runner 时间；另有三次，某个字段避免了错误结论，而不是只省下一点时间。

同一记录里诚实的一面，既来自使用者，也来自我们：

- 每一次调用在返回内容之前都要付出 schema 与 JSON 的代价，大约几百 token；“这次 run 是否通过”并不是免费问题；
- 自建服务必须能按构建标识，否则所有评估都可能基于错误的版本，`build.revision` 正是为此存在；
- 客户端缓存工具目录之后，服务端改动与客户端可见改动之间相差一次重连。

## 我们用自身工具改进本项目时看到的现象

我们通过本服务提供的能力来开发本服务：

- 77 个 job 的矩阵一次返回名册；失败 step 的 443 行日志通过一次窗口读取返回；
- 对 6 天前的一次 run 调用 `get_job_log(step=N)`，返回 `capture_closed` 而不是空文档。这促使我们抓取原始归档，并实测 step 分片在 56–70 分钟之间被压平；
- `ci_status.health.alerts` 列出 webhook 投递失败的 run id，修复动作从排查变成一次 `get_run`；
- 在一个有 24 个分支的仓库上查询，暴露出 workflow 显示名随分支变化的问题；只读本仓库不会发现该缺陷。
